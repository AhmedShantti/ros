# ADR 0003 — PostgreSQL Row-Level Security (tenant isolation)

- Status: Accepted (amended 2026-09-03 — see "Amendment 2026-09-03" below)
- Date: 2026-08-12
- Phase: 8

## Context

RLS is the final, database-level tenant-isolation boundary — effective even if
an application query forgets a tenant filter. The runtime must connect as a role
that cannot bypass RLS, and the tenant context must be transaction-local so it
cannot leak across pooled connections.

## Decision

### Roles
- **ros_migrator** — owner/migration role (runs `prisma migrate`; locally a
  superuser). Seeds system roles/permissions.
- **ros_app** — runtime role. `NOSUPERUSER`, `NOBYPASSRLS`, no DDL. The app
  connects via `APP_DATABASE_URL`. Granted only `SELECT/INSERT/UPDATE/DELETE` on
  identity tables (+ default privileges for future migrator-created tables).

### Context mechanism — `PrismaService.withAuthContext(scope, fn)`
The single authoritative mechanism. It opens one Prisma interactive transaction
and, as the first statement, runs
`SELECT set_config('app.user_id', $1, true), set_config('app.tenant_id', $2, true)`
(`true` = transaction-local, the parameterised equivalent of `SET LOCAL`), then
runs `fn(tx)` on the **same** connection/transaction.

Verified against `@prisma/adapter-pg` (probe + the RLS e2e as `ros_app`):
set_config and all queries share the connection; settings are discarded at
COMMIT/ROLLBACK; **no leak** to a later pooled request; **40-way A/B concurrency**
never cross-contaminates. `scope` originates only from a validated
principal/TenantContext — never client input. Both values are read in policies as
`NULLIF(current_setting(<key>, true), '')::uuid`, so a missing/empty context is
`NULL` → predicate false → **fail closed**.

**Nested transactions:** Prisma has no nested interactive transactions, so
`withAuthContext` is never nested. The request-level `TenantContextGuard`
resolves context in its own short transaction (memoised on the request); the
controller's service call runs a separate `withAuthContext` transaction. These
are sequential, not nested; each fully sets its own context.

### Tables & policies (14 policies)
Only `memberships` and `roles` carry a direct `tenant_id`; children inherit via
the parent (no `tenant_id` added — ADR 0001).

- **memberships** (ENABLE+FORCE) — SELECT and WRITE policies intentionally
  differ:
  - `SELECT`: `tenant_id = app.tenant_id OR user_id = app.user_id` — the
    user-scoped branch lets a user discover the tenants they belong to
    (`GET /auth/tenants`) **before** selecting one.
  - `INSERT/UPDATE/DELETE`: `tenant_id = app.tenant_id` **only**. A user can
    never create/modify/delete a membership in an arbitrary tenant via `user_id`
    (e.g. cannot touch their own tenant-B membership while operating in tenant A).
- **roles** (ENABLE+FORCE — amended 2026-09-03; see "Amendment 2026-09-03"
  below. Originally ENABLE only) — `SELECT tenant_id = app.tenant_id OR
  is_system`; writes `tenant_id = app.tenant_id`. The original rationale
  recorded here — "Not FORCE, so the owner (ros_migrator) can seed system
  roles" — is **superseded**: it conflated the absence of FORCE with
  `ros_migrator`'s unconditional superuser RLS bypass (which needs no FORCE
  exemption to seed system roles either way). Tenant admins (ros_app) cannot
  create system/other-tenant roles.
- **role_permissions** (ENABLE) — inherited via the parent role
  (`EXISTS role: tenant_id = app.tenant_id [OR is_system for SELECT]`).
- **membership_roles** (ENABLE+FORCE) — inherited via the parent membership
  (SELECT: tenant or own-user; writes: tenant only).

### Excluded tables (with reason)
- `users`, `credentials`, `sessions` — global identity / per-user, tenant-agnostic
  (ADR 0001); not tenant-scoped.
- `permissions` — global reference catalogue.
- `tenants` — the tenant registry itself (each row *is* a tenant); access is via
  membership at the app layer.

### Application authorization is retained
RLS is defense-in-depth, not a replacement. Authentication + TenantContext + RBAC
all remain active; RLS is the last boundary.

## Consequences
- The runtime cannot read/write cross-tenant rows even with a missing app filter.
- `app.user_id` is a second, transaction-local context variable (beyond
  `app.tenant_id`) required by the memberships dual-SELECT policy.
- Test/admin arrange for RLS tables uses the migrator/superuser client; runtime
  isolation is proven exclusively through `ros_app`.
- Indexes: `tenant_id` is already indexed on memberships and roles; child `EXISTS`
  policies resolve via the parent PK. No additional indexes required at this scale.

## Amendment 2026-09-03 — identity.roles FORCE ROW LEVEL SECURITY

**Ratified 2026-09-03 by explicit human governance action.**

Ratification text: *"The project approves amending ADR-0003 to permit enabling
FORCE RLS on identity.roles, while preserving the current system-role seed
path through ros_migrator and making no privilege change to ros_app."*

### What this amends

The original Decision above recorded `identity.roles` as `ENABLE` (no
`FORCE`), reasoning that omitting FORCE was *necessary* so that `ros_migrator`
(the table owner) could seed system roles (`tenant_id IS NULL`,
`is_system = true`) without an `app.tenant_id` session context. Investigation
recorded in `docs/reports/claude/full-srs-4day/2026-09-03_CI-1_security-isolation-release-gates.md`
§13.3 established this rationale was not correct as stated: `ros_migrator` is
a full PostgreSQL superuser (`rolsuper = t`), and superusers/`BYPASSRLS` roles
"always bypass row security, regardless of whether row security is enabled or
forced for the table they are accessing" (PostgreSQL's own documented rule).
`ros_migrator`'s bypass was therefore already unconditional before FORCE ever
entered the picture — the absence of FORCE was never actually load-bearing
for the seed path. This was proved experimentally against a disposable
database (not the persisted `ros` database, not CI): with FORCE enabled, the
system-role seed pattern (`tenant_id = NULL`, `is_system = true`, inserted by
`ros_migrator` with no `app.tenant_id` set) still succeeded unchanged, and
`ros_app`'s own read/write behaviour under its existing tenant-scoped
policies was unaffected either way (`ros_app` was never the table owner, so
ENABLE alone already fully governed it regardless of FORCE).

**The prior exception (ENABLE only, no FORCE, for `identity.roles`) is
superseded by this amendment.**

### Amended decision

- `identity.roles` SHALL now use `ENABLE` **+ `FORCE`** ROW LEVEL SECURITY,
  the same posture as `memberships` and `membership_roles`.
- System/platform role seeding remains through `ros_migrator` exactly as
  before — unchanged code path, unchanged privileges, unchanged behaviour.
  `ros_migrator`'s superuser bypass (not the absence of FORCE) is what always
  permitted this, and continues to.
- This amendment does **not** authorize any new runtime bypass of any kind.
- `ros_app` remains fully subject to RLS on `identity.roles` (as it always
  was — ENABLE alone already governed the non-owner runtime role).
- `ros_app`'s permissions/grants are **unchanged** by this amendment — no
  privilege was added, removed, or altered for `ros_app`.
- No additional FORCE exemption is authorized by this amendment, for
  `identity.roles` or any other table. The `FORCE_EXEMPTIONS` mechanism in
  the generated FR-PLT-014 CI gate (`test/tenant-isolation/rls-inventory.e2e-spec.ts`)
  is removed as a consequence — with `identity.roles` amended, the map has no
  remaining entries and is not retained as a dormant escape hatch for future
  use.

### Implementation

`prisma/migrations/20260903100000_identity_roles_force_rls/migration.sql`:

```sql
ALTER TABLE identity.roles FORCE ROW LEVEL SECURITY;
```

One statement; no grant changes, no policy changes, no application code
changes. See the CI-1 report's closure section
(`docs/reports/claude/full-srs-4day/2026-09-03_CI-1_security-isolation-release-gates.md`)
for the live-database proof re-run against this migration and the resulting
FR-PLT-014 disposition.
