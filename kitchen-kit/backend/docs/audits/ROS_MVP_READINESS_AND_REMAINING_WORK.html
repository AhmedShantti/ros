MVP Readiness

NOT READY — but design prerequisites for the critical path are clear

The repository holds a genuinely excellent foundation covering roughly one seventh of the SRS. Every revenue-generating domain is absent. No order can be created, no payment taken, no ticket fired, no receipt printed. A restaurant cannot operate on this system today.

The MVP is not blocked by unresolved design. Sales/POS — the critical path — has no open governance decision against it. The three unresolved schema items and the two blocked decisions all sit on Governance approvals, which is not on the MVP critical path.

Sequences

Optimistic — price resolution, Money and PIN run in parallel; the order aggregate proceeds without rework; tax needs only one pack; depletion reuses the existing ledger cleanly.

Realistic — the order aggregate churns once as pricing, tax and discount interactions surface; idempotency forces a cross-cutting refactor of existing write paths; branch scope forces revisiting query paths already written; the first country pack takes longer than expected because it is also the pack architecture.

Uncertainty factors

  • No client exists. Every requirement here is backend-only; a POS UI is an entirely separate and unestimated effort.
  • Idempotency is cross-cutting and touches routes already built.
  • Country-pack architecture is designed but unproven; the first pack validates or invalidates it.
  • Offline design pressure — building online-only risks an expensive retrofit later. Design decisions taken now should not preclude it.

14Executive summary

1 · What we have now

A rigorously built platform substrate covering roughly one seventh of the SRS: authentication with token rotation, tenant isolation enforced by 213 RLS policies across 62 tables and verified live against a non-bypassing role, tenant-scoped RBAC on all 123 routes, a tamper-evident audit chain, the full organisation hierarchy, a catalogue, an append-only inventory ledger with valuation, and — new since the audit — recipes with versioning and cycle detection. Seven of twenty-nine domains have executable code.

2 · What is missing for MVP

Everything that makes money. No order, no price resolution, no PIN login, no Money type, no tax, no payment, no receipt, no kitchen ticket, no stock depletion, no cash session, no reporting. Nothing in the system can complete a sale.

3 · The true MVP scope

One tenant, one brand, one branch. Dine-in and takeaway. Staff log in by PIN, build an order from a priced menu, take cash or an external card payment, print a compliant receipt, fire a ticket to the kitchen, deplete stock by recipe, and close the cash session — with tenant isolation, branch scope and audit intact, and a daily sales summary to read the next morning. Online-only. Single country pack.

4 · The #1 critical path

Price resolution + Money + PIN → Order aggregate → Payment + idempotency → depletion, tickets, cash close → minimum reporting. The order aggregate is the pivot: roughly 230 requirements sit downstream of it.

5 · What can run in parallel

Start now: branch-scoped RBAC (hardest to retrofit), scheduler/jobs (cheapest leverage, and it defuses a live partition risk), observability baseline, CI/CD. Anytime: audit query surface, settings resolver.

6 · What we should not build yet

Governance approvals — 17 ratified decisions and zero callable code; it delivers nothing until POS needs discount approval. Offline/Sync, Costing, Procurement, Workforce, CRM, central-kitchen distribution, integrations, floor plans, additional country packs.

7 · MVP exit criteria

  1. A staff member authenticates by PIN at a terminal bound to a branch.
  2. An order is created, priced from a resolved price list, taxed by country pack, and closed.
  3. Payment is taken and cannot be double-charged under retry.
  4. A compliant receipt is produced.
  5. A dine-in order fires a kitchen ticket that can be bumped.
  6. Completing the order moves the stock ledger by recipe expansion.
  7. The cash session closes with a computed variance.
  8. A manager reads a daily sales summary and cannot read another branch's.
  9. Every one of the above emits an audit entry, and the chain still verifies.
  10. Cross-tenant access returns 404 everywhere, proven by live probes with positive controls.

8 · The first ten work items, in order

  1. Money value object — BR-CORE-001/002, BR-FIN-001/003
  2. Catalogue price resolution — FR-MNU-021/022/023
  3. PIN authentication — FR-SEC-021/022
  4. Branch-scoped RBAC — FR-SEC-002/003/004 (parallel; retrofit cost rises daily)
  5. Scheduler/jobs — FR-DR-002 first, to defuse the partition-boundary risk
  6. sales schema + RLS + composite FKs — FR-PLT-003/010/011/012
  7. Order aggregate & state machine — FR-POS-001…040
  8. Idempotency layer — FR-API-020…023
  9. Tax engine + first country pack — FR-FIN-030…032, FR-LOC-020…022
  10. Payment & tender — FR-POS-060/065
