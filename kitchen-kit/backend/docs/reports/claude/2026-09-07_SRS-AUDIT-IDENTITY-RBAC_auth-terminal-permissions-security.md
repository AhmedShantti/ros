## 6. `src/modules/authorization-coverage.spec.ts`

**What it tests:** Pure filesystem/reflection-metadata static analysis — it `require()`s every `*.controller.ts` under `src/modules` and reads NestJS's own route/decorator metadata directly (`Reflect.getMetadata`); it **never** boots the Nest DI container, opens an HTTP server, or touches Prisma/a live database. It asserts: (1) route discovery sanity floor (>120 routes, ≥15 files); (2) route ids are unique; (3) every permission-bearing route declares an explicit `@AuthorizationTarget`, or is named with a reason in a (currently empty) `REVIEWED_TENANT_TARGET_ROUTES` allowlist; (4) every route with no `@RequirePermission` is named with a ≥20-character reason in `REVIEWED_UNPROTECTED_ROUTES` (20 entries — login/pin/refresh/logout/me, password self-service, tenant selection, terminal bind/read, health, sync transport, clock-in/out); (5) no allowlist entry references a route that no longer exists; (6) every declared `@AuthorizationTarget` is structurally valid for its kind; (7) the one T-12 inactive-branch exemption is used by exactly one route; (8) prints route/target-scope totals for reporting. This is exactly the governance-mandated "generated/enumerated authorization-coverage gate" the B1-3 ratified implementation authority required (governance register clause 17, item 2: "a generated/enumerated authorization-coverage gate so future scoped surfaces cannot ship unprotected").

**Does it need a live DB?** No — confirmed by direct static-analysis read and by two independent live runs this session.

**Result (run twice, independently, both times identical):**
```
Test Suites: 1 failed, 1 total
Tests:       2 failed, 7 passed, 9 total
```
Both failures share one root cause:
```
● EVERY route without a permission requirement is a reviewed auth-only route
  - Expected  []
  + Received ["POST /auth/registrations  (modules/identity/registrations/registrations.controller.ts#register)"]
```
plus the consequent `UNDECLARED` route-count census mismatch (21 actual vs. 20 expected).

**Verdict — real risk or allowlist/test drift?** **Allowlist/test drift, not a live authorization hole.** `registrations.controller.ts` confirms `POST /auth/registrations` (FR-PLT-020 tenant self-service signup) is deliberately public, rate-limited (`ThrottlerGuard`, IP-keyed), and validated by the same global strict `ValidationPipe` as every other route — exactly the same class of route as `POST /auth/login`, which **is** correctly allowlisted. The route was added without its corresponding one-line `REVIEWED_UNPROTECTED_ROUTES` entry. A separate prior report in this repository (`docs/reports/claude/2026-09-07_GOLDEN-PATH-BACKEND-CLOSURE_kds-refund-cashclosepolicy.md`) independently confirms these same 2 failures were "confirmed present before this task's changes via a clean-stash re-run" — i.e. this is a known, pre-existing, non-regressing drift, not something introduced recently. Fix is a one-line allowlist addition; no production authorization risk.

## 7. Special checks

**AUTH/SESSION:** Password login and PIN login are both real, fully tested, and architecturally sound — the POS/dashboard boundary (`typ:'pos'`, deny-by-default in `JwtAuthGuard`) is a genuine, independently re-verified anti-escalation control (11 e2e suites / 182 tests passing live against Postgres this session), and the September 2026 employee-identity hotfix (`dc746a9`) is confirmed correctly fixed and regression-tested. Tenant selection, refresh rotation/reuse detection, and the epoch-based revocation mechanism are all complete and fail-closed. The real gaps cluster in five places: **(1)** three of five SRS-mandated auth methods (employee card, biometric, SSO) simply don't exist and carry no governance deferral, unlike MFA, which is formally deferred (board `G4-2`); **(2)** password login has no account lockout at all — only IP+email rate limiting; **(3)** there is no admin-triggered cross-user forced logout, only self-service revocation on one's own password change/reset (no `UsersController` exists at all); **(4)** password minimum length is 8, not the SRS-mandated 10, and is not per-tenant configurable; **(5)** idle-session semantics don't exist as specified for POS/dashboard — only a single flat access-token TTL applies regardless of session type (the KDS-specific 8-hour portion is at least formally deferred). Terminal revocation is live-enforced on the very next request (not just at next login), which is stronger than a literal reading of FR-SEC-028 requires for its server-side half; the device-wipe half is out of backend scope by nature, and governance has explicitly left FR-SEC-028 open pending it.

**RBAC:** The permission-guard/scope-lattice architecture (`ScopeAuthorizationService` + `scope.ts` + `PermissionGuard`) is a well-built, ratified (D-2 REOPENED IN PART (2), ADR 0009), and now largely-enforced system: FR-SEC-001 through FR-SEC-005 are all COMPLETE_BACKEND at both the primitive and enforcement-across-the-business-surface levels, corroborated by a governance-mandated coverage gate (`authorization-coverage.spec.ts`) that currently shows only one cosmetic, pre-existing, non-regressing allowlist-drift failure. The permission catalogue itself is materially incomplete against SRS §15.2: an entire Procurement domain is absent, several Sales/Workforce codes are unimplemented, and SRS-named `security.*`/`api.key.manage`/`governance.view_anomalies` codes don't exist under those exact names. Standard-role coverage is thin — only 5 of 13 SRS-named roles ship as templates, deliberately, per a governance decision citing the still-missing SRS Appendix C — and role deletion/cloning endpoints don't exist at all. Segregation-of-duties enforcement is real but partial: DB-level hard-blocks (Decision D-7, ratified) exist for discount and cash-variance self-approval, but the SRS's own count-perform/count-post self-approval block is explicitly absent, no generic incompatible-pair warning mechanism or SoD conflict report exists, and — most notably — nothing prevents a user from granting a role permissions they don't themselves hold (a documented, still-open self-elevation gap, distinct from FR-SEC-016's named combinations). Tenant/branch scope correctness is strong: RLS is enabled+forced tenant-wide with a dedicated no-exemption gate, and branch scoping is a real, live-checked, non-leaking mechanism — though production multi-branch readiness for any given tenant additionally depends on a per-tenant migration scope-review condition whose current satisfaction status could not be confirmed from the repository alone. POS-only vs dashboard-only enforcement is complete and defense-in-depth (JWT audience check plus live per-request branch/terminal/employee re-verification).
