## A. Scope and method

Static read of controllers/services/permissions/seed-and-provisioning code on the backend, and the live-wired POS screen (`components/terminal/pos-live.tsx`, used when `DATA_MODE === "http"`) on the frontend. Explicitly excluded the frontend's separate in-memory "demo" simulator (`DemoPos`/`pos-payment.tsx`/`pos-floor.tsx` under `DATA_MODE === "mock"`) from golden-path credit — it is not wired to the backend at all (`app/(terminal)/pos/page.tsx:26-46`).

Two backend provisioning paths exist and were both checked because they disagree on the Cashier permission set:
1. `src/scripts/seed-dev-data.ts` — a **local-dev-only** convenience script, explicitly documented as not the shipped policy (its own comment at `seed-dev-data.ts:245-249`).
2. `src/modules/identity/authz/canonical-role-templates.ts` (`ensureCanonicalRole`) — the **production** path actually used by `POST /auth/registrations` (self-service signup) and `WorkforceEmployeesService.create`/`assignRoleToEmployee` (the real Employees UI), per `docs/reports/claude/2026-09-05_LIVE-DEMO-HOTFIX-1_*.md` and `2026-09-06_DEMO-OPS-HOTFIX-2_*.md`. **This is the one that governs the actual live demo**, since the demo onboards through signup, not through re-running the dev seed script.

All permission findings below cite the canonical-role-templates path as authoritative for demo purposes, with the dev-seed discrepancy called out separately where it matters.

## C. Notes on severity ordering

- Step 16 is listed BLOCKED_FRONTEND rather than BLOCKED_PROVISIONING because the dine-in/no-table default fires on literally the first order a fresh demo tenant creates, before any station/routing question is even reached — it is the first thing a rehearsal will hit.
- Step 23 is the only step where the gap is a genuine missing-permission defect in the shipped canonical-role provisioning code (`canonical-role-templates.ts`), not merely a one-time manual setup task an Owner can complete through the UI (unlike Steps 16's routing config or 21's Drawer, both of which have a real Operations-UI path already built by prior hotfixes).
- Step 22 is a real, shippable gap (backend complete, frontend never wired) rather than a defect — smallest fix is additive UI only, no backend change needed.
